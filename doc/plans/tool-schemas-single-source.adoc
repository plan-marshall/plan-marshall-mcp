== Tasks

The comparison made when this package was planned (link:../../../pm-mcp-core/doc/plans/schema-files-foundation.adoc[`schema-files-foundation`] states the rule that a schema is one file the specification includes) found these differences between the spec block and the file; the spec block also carries `$schema`, `title` and a top-level `description` that the flat-schema rules refuse in an `inputSchema` (`ToolSchemaRules`).

* `pm_state`, `pm_do`: the descriptions of `plan_id`, `epic_id`, `entity` (`pm_do` also `link`) differ in wording; the properties and `required` agree.
* `pm_wait`: no properties; the two agree.
* `pm_build`: the spec has the property `criterion`, the file does not.
* `pm_lsp`: the spec has 12 properties, the file 7 (`depth`, `direction`, `to_character`, `to_line`, `to_path` are only in the spec); the descriptions of `op`, `path`, `line`, `character` differ.
* `pm_skill`: the file has `plan_id` and `epic_id`, the spec does not.

. *Reconcile first, per difference*: a wording difference is aligned to the better text, in the file. A property only in the specification is either work not built yet (it stays out of the file; its block stays inline until the package that builds it) or a specification error (corrected with evidence); a property only in the file is either an implementation detail the specification should state (the specification is corrected) or a leftover (the file is corrected). The decision of each difference is written next to it, here, before the first edit.
. *One file per tool*: the `inputSchema` of every tool whose spec block and file agree after the reconciliation is the one statement; the specification block is replaced by an include of the tool file (an include into the sibling checkout, `../../../../plan-marshall-mcp/pm-mcp-server/src/main/resources/pm-mcp/tools/<tool>.json`, from the document), and the `description` of the tool stays in the file with it. The spec keeps its prose around the block.
. *A tool with a property that is not built yet* (`pm_lsp`, `pm_build`) keeps its inline block, which `trace.py` reports and does not fail (link:../../../pm-mcp-core/doc/plans/schema-files-foundation.adoc[`schema-files-foundation`]); the package that builds the property moves the block.
. *The check that stays a test*: `ToolSchemaRules` is applied to every tool file by `FlatSchemaValidatorTest` and `McpSocketTest`; a test that every tool file listed by the server has the properties its description names is added only if the reconciliation shows one that is missing.
. *Documents here*, in the pull request beside this one: the two specification documents as above; `trace.py` resolves the includes into this repository.
. *Not in this package*: the `bundle-manifest.json` schema (`harness-integration/02-bundle-manifest.adoc`) has no implementation in any repository yet; it stays inline until the package that builds the manifest, which then follows the rule.

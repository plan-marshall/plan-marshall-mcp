== What

The leftovers of link:question-loop-verification.adoc[`question-loop-verification`]. That package measured every item Q1 to Q7 and R1 to R4 at smoke scale (3 runs, 2 fixtures), so every verdict reads _not at the specified scale_ (link:../../../plan-marshall-documentation/doc/specification/evaluation.adoc#results[Evaluation Reference, Results] and its limits). The mechanisms are described in link:../../../plan-marshall-documentation/doc/developer/question-loop-experiment.adoc[The Question-Loop Experiment]; the code is kept on the pushed branch `verification/question-loop-experiment` of this repository (`488ce47`). This package turns the durable parts of that code into maintained code, settles what the smoke run left open, and repeats the measurement at the specified scale of 20 runs per fixture and host, warm and fresh, with the criteria of the original package — except the two the operator fixed before the first run (task 2). The criteria are fixed before the first measured run and not changed by it: a criterion change is decided by the operator before the first run of the follow-up, on reasons not drawn from the follow-up's own runs, and recorded in this package.

* _Evidence._ Every run's evidence — `runs.jsonl`, `invocations.jsonl`, the stub logs, the per-invocation archives and the answer audit — is kept and pushed outside any plan worktree: on the branch `question-loop-follow-up` of the private repository `cuioss/plan-marshall-telemetry`, beside the scenarios kept on that repository's branch `verification/question-items`, before the plan's worktree is removed. A published figure whose source is not in that store is not a result.

* _Fixtures per item._ Q1 to Q7 and R3 run on 2 fixtures each — the count of the smoke scale, held so that the two scales compare item by item — where Q1 to Q5 and R3 take the loop tasks of the corpus topic `question/apply-answer`, Q5's bound tasks come from `question/ask-or-proceed`, Q6 takes the quorum fixtures of the two vote links, Q7 takes the fixtures of Q2 on Claude Code only, and the original descriptions are the controls of Q2. R1 and R2 run on the probe, R4 runs on the probe for small work and on the two scenarios named in task 10 for large work. Task 6 states the resulting invocations per item and host before the first run.

The run costs differ by orders of magnitude and are planned with that in mind (task 6): OpenCode runs are cheap (60 runs of R3 cost 0.22 USD), Claude Code costs dollars per invocation of 24 runs (about 2.3 to 2.9 USD), Antigravity reports no figures; the wall time is the cost of R1 (6.6 h for 12 OpenCode runs) and R2 (9.3 h for 24 runs).

== Tasks

Ordered by dependency: the extraction first, then the decisions and the preparation of the hosts, then the measurements, then the values they settle.

=== 1. Extract the durable experiment code into pm-e2e

[horizontal]
Deliverable:: The durable parts of the experiment as maintained code: the stub MCP server with leases, fencing and replay; the driver that launches the harnesses through `pm-exec`; the fixtures (corpus cache and probe); the result evaluation and aggregation, with the `evidence_missing` guard and the per-invocation archive; the per-host classification of early exits and quota. The developer document is updated to the extracted form. The evidence outputs are written in the form the store of this package takes.
Lands:: pm-e2e, under the rules of this repository (Maven, JUnit 5, no Mockito, `package-info.java` per package). The measurement is gated by properties, so that no normal build calls a harness; what stays experiment-only stays gated or on the branch. The developer document in `plan-marshall-documentation`.
Done when:: the extracted classes have their own tests at the coverage bar of the repository, `verify`, `verify -Ppre-commit`, `verify -Pcoverage` and `verify -Pintegration-tests` are green with the measurement gate off, a gated run reproduces one smoke group of the results — the same verdict per item and every count within one run of the smoke group's figure, the group and its figures named in the plan's record — and the developer document describes only what is in the tree.

=== 2. Decide what the package owner owns

Each decision is recorded with its evidence in the Evaluation Reference or the owning specification before the runs that depend on it; none is settled by editing a criterion in passing, and this package changes no criterion itself.

[horizontal]
Deliverable:: A recorded decision for each of the following.
* *R3 `CALL_CUT`.* A held call that the host cuts (Antigravity at 180 s) is carried on by the same worker. The measured finding fails on every host because the criterion counts the cut as undetected. _The operator decided before the first measured run (2026-10-28)_: the criterion changes, so that a cut call the worker survives is not a lost continuation, and the profile's `cut` setting stays as it is. The changed criterion is written into the Evaluation Reference before the first run.
* *Q4 reference form.* One deepseek fresh/default run missed for a format-only reason: it submitted `f(7) == [...]` instead of the bare list, and `followsReference` compares exactly. _The operator decided before the first measured run (2026-10-28)_: the item's reference form accepts `f(7) == [...]` as a match for the bare list, so a format-only deviation is not a miss. The accepted form is written into the Evaluation Reference before the first run.
* *R2 at 24 hours.* Not run, by the operator's decision of 1 hour at most. It stays _not run_ unless the operator decides otherwise; record the decision either way.
* *R4 scenario choice and forcing.* How the ask of the large-work scenarios is forced on a host that does not ask unless forced, whether large work has a fallback form, and which scenarios carry it (see task 10).
* *Q7 host scope.* Q7 is hard-wired to Claude Code: make it host-generic, or record why it stays Claude Code only. Antigravity skipped Q7.
Lands:: link:../../../plan-marshall-documentation/doc/specification/evaluation.adoc#limits[Evaluation Reference, Limits] and, where a value follows, its owning specification through `pm-mcp-core` / `client-profile-measured-values`.
Done when:: every decision is recorded with its reason, the two criterion decisions of the bullets above are recorded in their decided form, and the tasks below name the decided form.

=== 3. OpenCode: the question loop's findings and the measurement setup

[horizontal]
Deliverable::
* *The question loop's findings only.* Whether the profile or the version pattern changes for what the specification now states — the supported version range, `run --standalone` with the project from `PWD`, the version probe, the `events` mapping (the open question `opencode-event-source`), the tool names — is the work of the Roadmap Milestone 14 item that verifies and ships the OpenCode 2.x profile. This package names that item as the owner of those findings and changes nothing of the profile for them.
* Define the session id pointer for the `sessionID` field of OpenCode's output lines (the schema's `session_id` expects a JSON Pointer); the operator accepted the proposal.
* Investigate the refusal in R2 warm/300 after a stub restart: generations 2 and 3 of run `R2-opencode-warm-probe-resumability-001-9356d016` refused to call the tools, saying they were removed from the tool catalog although the stub offered them (OpenCode session `ses_e87037d5dffejxVc1hFQphFa3p` in `opencode.db`). The investigation treats code mode as a candidate cause (HYPOTHESIS: the harness offers the server's tools behind its code tool by default, not as direct tools) and compares direct tools with code mode; name the cause, or record it as a finding of the host, and record the result either way.
* *The configuration of every measured OpenCode run.* Every OpenCode run uses the profile's `headless.inline_settings`, and the effect of each key is checked before the first measured run, never its acceptance alone (link:../../../pm-mcp-core/doc/implementation-watch/client-profiles.adoc#PM-WATCH-CLIENT-17[PM-WATCH-CLIENT-17]). The unset defaults are the matched control wherever a result may depend on a setting. By the operator's decision that control runs for the cheap items only: Q1 to Q7 and R3 on OpenCode run twice, once with the inline settings and once on the unset defaults; R1 and R2 are measured once, with the inline settings in force and no second, unset-defaults arm. The package states that scope so that no figure of R1 or R2 claims a control.
* *The data home.* A 2.x login is not in `auth.json`, so the per-worker data home of the specified setup is not established (the open question `opencode-worker-login`). By the operator's decision OpenCode runs serially on the operator's data home, as the smoke run did; this package records that decision and the departure from the specified per-worker data home, and no figure claims a per-worker data home.
* Record the model choice per role in the profile verification: `gpt-5.4-nano` reached the tools in only 44 of 108 runs, `deepseek-v4.1-flash` is the model the measurement used.
Lands:: the OpenCode profile and the profile verification in `pm-mcp-core`, through `client-profile-measured-values`; the driver of task 1 here.
Done when:: the session id pointer is defined and named for `client-profile-measured-values` to apply to the profile, the tool-catalog refusal is explained or recorded as a finding of the host, the profile and the version pattern carry no change that belongs to Milestone 14's item, every measured OpenCode run records that it used the inline settings with its arm, the effect check of each key is recorded before the first measured run, the control's scope is recorded, the model each role's runs used is recorded, and the serial data home and its departure are recorded.

=== 12. Settle the resumability values and the profile schema

[horizontal]
Deliverable::
* The measured candidates (hold and resume up to 3,600 s on Claude Code, OpenCode 2.x and Antigravity) sit beside the unchanged shipped values (`false` and `null`) in link:../../../pm-mcp-core/doc/specification/client-profiles/01-profile-schema.adoc#headless-resumability[Client Profiles § Resumability]. The values are settled from this package's own driver runs, on the probe of task 1, so that no value waits for a stage built elsewhere; the stage `resumability` of `pm-operator profile verify` repeats this measurement once `question-continuation` builds it, and the rule of that section that every value comes from the stage is corrected to this order by the owning package.
* The stage expects a resume of a missing session to fail at once, but OpenCode and Antigravity start a new session instead: the operator decides whether the stage or the expectation changes, and the decision is recorded here.
* The profile schema has no place for four findings: whether a model reaches the tools, a missing session that starts a new one, a cut call the worker survives, and the OpenCode tool-catalog refusal of task 3. Decide the schema additions. The form of such an addition is the member `headless.inline_settings`: a member in the `required` list of the profile schema, `null` where a harness has none, validated by `core.profile` and merged into the launch. The settled values go into the profile that ships the 2.x range `>=2.1.0 <3.0.0`; where Milestone 14 has not shipped it when this task is reached, they go into the evaluation reference only, the profile keeps its provisional `inline_settings`, and each `resumability` form not measured stays `false` or `null` — the operator confirms that.
Lands:: `pm-mcp-core` (the client profile schema, the shipped profiles, the profile verification stage), through `client-profile-measured-values`, with its documentation in `plan-marshall-documentation`; the Evaluation Reference rows here.
Done when:: the measured values per profile are settled from this package's runs and recorded with their evidence, the specification of the stage and its expectation agree with the measured hosts, each finding has a place in the schema or a recorded reason for none, each open decision of this task carries the operator's recorded decision, and the values and the schema changes are named for `client-profile-measured-values` to ship — where Milestone 14's 2.x profile has not landed, they stay in the evaluation reference and the shipped profile keeps its provisional values, as the third bullet states.

= Model Verification Corpus
:toc: left
:toclevels: 3
:nofooter:

== Goal

`PM-MCP` leaves the judgment in a running plan to model roles: triage of build failures, review comments, and static-analysis findings; re-planning; security, simplify, and self-reviews; the screening of untrusted text (https://github.com/plan-marshall/plan-marshall-documentation/blob/main/doc/concepts/harness-as-worker/roles.adoc[Harness as Worker, Roles]). Which role may run on which harness, model, and effort, warm or fresh, is a configuration (https://github.com/plan-marshall/plan-marshall-documentation/blob/main/doc/concepts/harness-as-worker/roles.adoc#configuration[Roles are configuration]); whether a configuration is good enough is a measurement.

This corpus is what that measurement runs against: verified questions, each with the answer the operator accepts. It answers, per role and configuration:

* *Does the role decide as the operator would?* The agreement with the references, against the level the operator sets (80 % in the evaluation).
* *Does a change keep it so?* A new model, a new prompt, a new skill, or a new harness version is run against the same items, and the figures are compared.
* *Which configuration should the role run on?* The cheapest harness, model, effort, and form that meets the level (<<_grade_a_model_and_effort_level_for_a_role>>).
* *Are the items themselves right?* Answers of several models per item show which items lack evidence or are contested (<<_improve_the_corpus_with_several_models>>).
* *Is warm as good as fresh?* The same items in a warm worker and in fresh jobs.

It outlives the evaluation tooling that created it (https://github.com/plan-marshall/plan-marshall-documentation/blob/main/doc/specification/evaluation.adoc[Evaluation Reference], items E7, E9, E13): the items, their schema, and their rules are independent of any driver.

== Structure

=== Layout

[source]
----
test/model/verification/
├── README.adoc                     this document
├── validate.py                     checks every item (stdlib Python)
├── schema/
│   └── verification-item.schema.json
├── context/
│   ├── worker/                     the launch context of a worker: shim, core conduct, task protocol
│   ├── roles/                      the contract of each role (one file per role)
│   ├── grading/                    the judge of open answers, the screener and level 1
│   └── commit-typing/              a project rule items require (input.context)
└── <topic>/<subtopic>/<slug>.json  one item per file
----

The id of an item is its path below this directory without `.json` (`triage/build/bt-03-fapi-ci-502`); its `topic` is its directory. Items that belong to one case share a `group` (the split and combined questions of one self-review).

=== Topics

[cols="2,2,1,4", options="header"]
|===
|Topic |Role |Items |Content

|`triage/build` |triage-build (5), triage-ci (3) |8 |build and CI failures of real plans: fix, retry, accept, reject, suppress, or ask the operator
|`triage/pr-comment` |triage-review |10 |real review comments on pull requests: fix, reply and resolve, or escalate
|`triage/sonar` |triage-analysis |8 |real static-analysis findings: fix, suppress, accept, or ask the operator
|`planning/replan` |replan |4 |a running plan whose situation changed (base moved, a reviewer's file limit, a broken dependency, a red baseline): the revised plan
|`review/security` |review-security |4 |diffs with seeded security defects, one control without
|`review/simplify` |review-simplify |4 |diffs with seeded needless complexity, one control without
|`review/self-review` |review-requirement (4), review-code (4), self-review (4) |12 |four diffs with a requirement, each asked split (requirement: `review-requirement`; code: `review-code`) and combined (`self-review`, comparison items that grade no role)
|`decision/*` |worker (generic) |24 |closed decisions of a running plan: remediation, triage, scope, build classification, commit type, gate; they also grade the quorum roles `quorum-a` and `quorum-b` and calibrate every quorum declaration of the adjudication unit on the items of its decision kind (tag `decision-kind:<kind>`, link:../../../../pm-mcp-core/doc/specification/model-work/10-decision-quorum.adoc#quorum-calibration[Model Work Specification, Quorum Calibration])
|`skills/commit-typing` |worker (generic) |20 |decisions whose answer follows a project rule that exists only in a role skill; the item names the skill in its tags
|`screening/untrusted-text` |screener |45 |real review comments (clean) and injected instructions (suspicious)
|===

The `role` field of an item, not its path, decides which role it grades: a role's qualification grades it on the items whose `role` names it plus the generic items (`role: worker`) for every `writer` and `read_only` role; items with `role: self-review` are comparison items and grade no role. Items with `review.status` `draft` or `confirmed` count; `contested` and `retired` items do not (link:../../../../pm-mcp-core/doc/specification/model-work/01-roles-and-configuration.adoc#qualification-topics[Model Work Specification, Corpus Topics of a Role]).

=== The item

An item is a JSON object in the format of `schema/verification-item.schema.json`. Its fields:

[cols="1,4", options="header"]
|===
|Field |Meaning

|`id`, `topic`, `role`, `title`, `tags`, `group`
|identity: the path, the directory, the configured role that answers it, a short title, free tags (for example `requires-skill:<uri>`), the case group

|`input.question`
|the question the model is asked

|`input.facts`
|exactly the text the model sees besides the question; complete repository-relative paths; untrusted text quoted as data; never the answer

|`input.choices` / `input.answer_schema`
|the options of a closed answer, or the JSON Schema of an open one

|`target.answer`, `target.rationale`, `target.alternatives`
|the reference answer, its reason, and other answers the operator accepts

|`target.items`, `target.expected_empty`
|for open answers: the rubric items (seeded defects with location and the questions they belong to, or the essential properties of a revised plan); a control expects an empty answer

|`grading.method`
|`exact_choice` or `label` (the answer equals the reference or an accepted alternative), `rubric_items` (the share of `target.items` found; a control scores 1 only when empty), `rubric_properties` (the share of the properties met); `grading.judge` names the judge of a rubric

|`input.context`
|corpus files the answering role must have besides question and facts, below `context/` (for example the project rule the `skills/commit-typing` items test)

|`provenance`
|`kind` (extracted, hand-made, fetched, written), `created`, and only lasting anchors: `origin` (repository, commit, pull request, branch, path, line, a lasting URL, and a citation of a non-public record such as a plan's log entry), `based_on` (the repository, commit, and path of the real code a hand-made case was written against), and `history`, dated sentences that stay meaningful when every tool and plan of the time is gone

|`review`
|`status` (`draft`, `confirmed`, `contested`, `retired`), by whom, when, with notes; draft and confirmed items count towards a role's agreement level, contested and retired items do not

|`contamination`
|what in this or another item gives the answer away, and which items must not share a warm session

|`canary`
|the corpus canary string; a model that reproduces it has seen the corpus
|===

Results are never stored in an item. A run records the corpus revision (the commit) it used; its results live with the run.

=== Why this format

The format takes over what the established evaluation formats share:

* the sample core of Inspect AI (`id`, `input`, `target`, `choices`, `metadata`), so the items map onto it field by field;
* grading per item, as promptfoo's assertions do (`equals`, `llm-rubric`), instead of one grader per file;
* results kept apart from the items, as the shared result schema of Every Eval Ever does;
* a canary string in every item, the contamination guard BIG-bench introduced.

It adds what a reviewed, long-lived corpus needs: the review status with its history, the provenance of every case, accepted alternatives, rubric items with locations, and contamination notes between items. One file per item keeps every change of a reference a reviewable diff.

== How to use

=== Validate

[source,bash]
----
python3 test/model/verification/validate.py
----

It checks every item against the schema and the rules the schema cannot express: the id equals the path, ids are unique, the canary is present, a closed answer is one of the choices, a rubric has items unless the item is a control, context files exist, and provenance, review, and grading name no transient tool, stage, or local record path. Exit code 0 when every item is valid.

=== Measure a role

A measurement gives each item to a worker of the role and compares its answer with the reference. Any harness that can run a model can do it:

. *Give the worker its context*: the product's role qualification runs every item under the launch contract of production (the project checkout as working directory with the project's own instructions, the compiled and extension skills of the role and the project), except an item that names its own `input.context` (for example `context/commit-typing/`), which runs in an empty working directory with those files, because its answer must rest on them alone. Outside the product, `context/worker/` holds a launch context (the shim, core conduct, the task protocol) and `context/roles/<role>.md` the role's contract. Answers are only comparable under the same context.
. *Pose the item*: `input.question` and `input.facts` as the task, `input.choices` or `input.answer_schema` as the answer form.
. *Run it in both forms* where the role may be warm: one fresh job per item, and one supervised worker that takes the items one after the other.
. *Grade it* by `grading.method`: `exact_choice` and `label` compare with `target.answer` and `target.alternatives`; the rubric methods go to the judge (<<_grade_an_open_answer>>).
. *Record the run* with the corpus revision (the commit), the configuration (harness, model, effort, form), and per item the answer, its rationale, and the score; never in the items.

For Inspect AI an item maps to a sample with `FieldSpec(input=…, target="target", id="id", choices=…)` or a small record function. The evaluation ran the corpus with its own driver, a supervised job runtime with configurable roles (https://github.com/plan-marshall/plan-marshall-documentation/blob/main/doc/specification/evaluation.adoc[Evaluation Reference]).

=== Grade an open answer

A rubric item is graded by a judge model without tools that sees the question, the facts, the reference items, and the answer, and returns the items met with a score from 0 to 1. Its prompt and rules are in `context/grading/judge.md`; keep them unchanged between runs that are compared, and store every judgement with its reason beside the run, so it can be read back and disputed. The screener of `screening/untrusted-text` is specified in `context/grading/screener.md`.

=== Add or change an item

. Take a case from a real plan (its record, the code at its commit) or write one by hand against real code; the evaluation's extractor (in git at commit `a6333d2`, `scripts/fixtures.py`) shows one way to cut facts out of plan records.
. Write the item: facts without the answer, complete paths, untrusted text quoted; a draft reference with its reason; provenance with lasting anchors only; `review.status: draft`.
. Run `validate.py`.
. The operator confirms or corrects the reference; set `review.status: confirmed` with `by`, `date`, and a note.
. Commit one item per change where possible, so every reference change is one reviewable diff.

=== Add items from real plans

`PM-MCP` records every decision of a running plan with the facts the decider saw and the decision finally taken (the user's answer, or a later correction), and the operator verb `pm-operator decisions export --out <dir>` writes the judgment decisions as items of this format with `review.status: draft` (link:../../../../pm-mcp-core/doc/specification/model-work/11-decision-records.adoc#corpus-export[Model Work Specification, Corpus Export]). The export never writes into this directory and never sends anything anywhere. To take an exported item into the corpus:

. Read it in full: its `input.facts` carry the project's real code and records; remove what must not be kept, and keep untrusted text quoted.
. Check the reference against `review.notes`: a user's answer or a correction is the operator's own decision; a decision a role or a quorum took alone is unconfirmed and needs the same review as a written item.
. Drop items tagged `evidence-incomplete` unless the facts still carry what the reference rests on.
. Move the item to its topic directory under a slug of this corpus (its id must equal its path), run `validate.py`, and continue with the steps above.

Exported items of questions are generic (`role: worker`) and land in `decision/question`; the other judgments land in the topic of their role (`decision/remediation`, `triage/pr-comment`, `planning/replan`, `decision/change-type`, `decision/gate`). Server-rule decisions are never items: `--calibration` writes them as calibration rows for the thresholds, outside the corpus.

=== Add questions from plan-marshall runs

Before `PM-MCP` runs real plans, the questions of real planning already exist in the records of `plan-marshall` runs: the decision logs `.plan/local/plans/*/logs/decision.log` and `.plan/local/archived-plans/*/logs/decision.log`, the clarifications in `request.md`, and the resolutions in `solution_outline.md`. Their phase 1 to 4 questions (outline approach, granularity, placement, and test strategy; refine interpretation; posture; the review gate) are harvested into draft `decision/*` items: the question and the facts the asker had as input, the options as `input.choices`, and the answer actually given as the reference (https://github.com/plan-marshall/plan-marshall-documentation/blob/main/doc/roadmap.adoc[Roadmap]). The harvest classifies every item by its decision kind with the tag `decision-kind:<kind>` (link:../../../../pm-mcp-core/doc/specification/model-work/10-decision-quorum.adoc#decision-kinds[Decision Kinds]): each quorum declaration of the adjudication unit is calibrated on the items of its kind (link:../../../../pm-mcp-core/doc/specification/model-work/10-decision-quorum.adoc#quorum-calibration[Quorum Calibration]), so only classified items let a quorum decide. Until items of a kind exist, its quorum declaration does not decide, and while none decides every question set reaches the user; this is the intended safe behaviour, never a fault. The cases where the user answered against the recommendation are the important ones: they are the negative examples that show when an automatic decision would have been wrong. The harvest follows the steps of <<_add_or_change_an_item>> and the provenance rules below (a plan's log entry is cited as a non-public record, never by a local path); the decision export extends it once `PM-MCP` runs plans.

=== Improve the corpus with several models

A single model that answers an item wrongly says little about the item. Several models and forms that answer it the same way say a lot. The corpus is therefore improved by running each topic on several configurations (at least two models and both forms, warm and fresh) and reading the answers per item, not only the agreement per run, for example in a table like this:

[source,bash]
----
# for every item: the answer of every run, side by side, on one corpus revision
item                         reference          small/fresh   small/warm   large/fresh  large/warm  class
triage/build/bt-07-…         fix (accept)       fix           fix          fix          fix         stable
----

Each item gets a class from the answers of all runs:

[cols="1,3,3", options="header"]
|===
|Class |What the answers show |What to do

|`stable`
|every run agrees with the reference or an accepted alternative
|nothing; the item discriminates nothing between these configurations, but anchors the level

|`model-limited`
|some runs agree, some do not
|nothing on the item; the difference is the model's or the form's, and is what the grading of a configuration measures

|`split`
|no run agrees, and the runs disagree among themselves
|read the rationales: the case may be contested (record `target.alternatives`), or the facts may be ambiguous (sharpen them)

|`item-suspect`
|no run agrees, and every run gives the same other answer
|review the item before blaming the models: the facts may lack what the reference rests on, the reference may not match the definition of its option, or the case may be contested
|===

The review of an `item-suspect` or `split` item reads every run's rationale beside the reference and the facts, and ends in one of four outcomes, written into `review.notes` with the date:

. *The facts lack the evidence*: add it (the code, the log line, the decision the reference rests on) and run the item again. In the evaluation, `triage/pr-comment/pr-08` was answered wrongly by every run because its facts showed a review bot's claim but not the code that refutes it; with that code in the facts, every run answered it as the reference does.
. *The reference does not match its option's definition*: correct the reference and keep the earlier answer as an accepted alternative where it stays defensible (`triage/build/bt-07`).
. *The case is contested*: keep the reference and record the other defensible answer in `target.alternatives` (`triage/pr-comment/pr-07`, `triage/pr-comment/pr-10`, `triage/build/bt-06`).
. *The models are wrong*: keep the item unchanged; it is what the corpus is for (`triage/build/bt-05`, where the runs did not converge).

Only runs on the same revision of an item are compared. A reference changed after a run makes that run's figure provisional: re-score its stored answers for a closed item, run it again for changed facts, and say which of the two the figure rests on.

The corpus's own history shows the effect: after the first Stage 2 runs, five items were `item-suspect`; resolved this way, PR comment triage went from 70 to 80 % to 80 to 90 % on the same models, while build triage stayed below the level, because its remaining misses are `model-limited` and `split`, not item defects.

=== Grade a model and effort level for a role

The second use of the corpus: deciding *which configuration* a role should run on. A configuration is one role artifact (harness, model, effort, form; https://github.com/plan-marshall/plan-marshall-documentation/blob/main/doc/concepts/harness-as-worker/roles.adoc#configuration[Roles are configuration]); the corpus topics of the role are its test.

. *Choose the matrix*: the candidate configurations of the role, for example the small and the larger model of each harness, at two effort levels, warm and fresh. Each candidate is one role artifact in a configuration set of its own.
. *Run the role's topics* on every candidate, on one corpus revision, with its draft and confirmed items.
. *Read per candidate*: the agreement level against the operator's threshold, the gap between warm and fresh, the cost per item (priced units, and USD where the harness reports it), and the time per item.
. *Choose* the cheapest candidate that meets the threshold, with warm only where it stays within the allowed gap to fresh. A role whose every candidate fails stays unqualified, and its tasks take the conservative server fallback of PM-WORK-6.
. *Record* the result per role and configuration with the corpus revision, so that a later run (a new model, a new effort level, a new harness version) is compared against it, and a configuration that falls below the threshold is noticed.

In the evaluation this was done by hand for two levels per role (https://github.com/plan-marshall/plan-marshall-documentation/blob/main/doc/specification/evaluation.adoc#results[Evaluation Reference, E7]): the reviews met the level on Sonnet, warm and fresh; Sonar triage met it fresh on the small model and warm only on Sonnet; build triage and re-planning met it on no level tried. The product function is role qualification (https://github.com/plan-marshall/plan-marshall-documentation/blob/main/doc/requirements/16-model-work.adoc#PM-WORK-6[PM-WORK-6]).

=== Keep it clean

* Never paste items into prompts outside a verification run, and never into training or tuning data.
* Do not run items that give each other's answer away in one warm session (`contamination`).
* Retire an item (`review.status: retired`) instead of deleting it, so earlier runs stay interpretable.

== Origin

The corpus was started on 2026-10-04 with cases from real plans of `cuioss/API-Sheriff` and `cuioss/plan-marshall` (triage, re-planning), hand-made diffs against the real code of both repositories (reviews), closed decision tasks written on 2026-10-01, rule-following tasks written on 2026-10-03, and real review comments with written injections (screening). The confirmed references were checked against the answers of two models, warm and fresh; five were resolved from those answers and two gained accepted alternatives (see the items' `review.notes`). Public datasets are selected for the corpus and are to be fetched at a pinned commit, never stored here, once the loader of the work package `question-corpus-public-datasets` exists; `ATTRIBUTION.md` lists each with its licence and holders.

=== Provenance rules

* *Name only what lasts*: a repository, a commit, a pull request, a branch, a path, a public URL. A plan's local record (its logs and findings under the operator's working copy) is not retained; it is cited by the plan's name and the entry, never by a file path.
* *Never name the tooling of the time*: scripts, fixture files, verification ids, and stages change or go; the `history` says in plain words what happened and when.
* *Carry what the answer needs*: a rule, a skill, or a document an item depends on is copied below `context/` and named in `input.context`, never referenced where it may disappear.
